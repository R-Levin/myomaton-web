## Proposed walkthrough and review gate

1. **Give the same interview two entry points.** Open separately owned disposable cases. Show one Review-led case with exact fixture Review and submission linkage, and one direct-start case without Review evidence. Both enter the same engine after authorization. Carry only sanitized facts from the [C0 business brief](miopages-c0-business-brief.md) and website observations. Use the [strategy recovery](https://github.com/R-Levin/myomaton-web/commit/2c6a41f22a811090b3a24d3f84607c41f2b33cc4) as planning evidence. C2 is a separate negative isolation check.
2. **Make a single business choice visible.** Ask who should take the next step after reading about Standard Launch and what they should understand about the handoff. For example, a prospect who already has a site needs clarity about what MioPages reviews and retains. A prospect starting fresh needs clarity about which business material to supply. These are alternative rehearsal answers. Show that the follow-up, readiness finding and proposed Intro emphasis differ, using existing scoped history. The Operator sees the actual draft evidence, with open questions and the fixture provider clearly labeled.
3. **Carry one exact revision through real authority.** Use the existing proposal writer to capture the Operator's editorial choice and rationale for a text-only `/service` Intro on the inactive fixture. Tie that choice to the reviewed draft version and an existing projection-eligible fixture fact. Leave unconfirmed claims in the staged draft. Record exact approval through an authenticated fixture-only customer mandate, then independently review the projection with a separate test principal. Issue through the protected WordPress path. The test approvals demonstrate authority checks on disposable data. The customer-facing preview later in the flow represents a pending full-site review.
4. **Render what arrived.** Use the existing integration harness for actual signing, request authentication, PHP validation, off-webroot storage and receipt reconciliation. The [PHP compatibility harness](../wordpress/miopages-delivery/tests/core-pull-compat.php) intercepts network I/O. Label this local transport as simulated networking and refer to the closed rehearsal for real HTTPS evidence. The narrow new seam for owner review is a read-only renderer input that selects the exact digest-verified staged release, accepts its one supported Intro and reuses the fixture's escaped rendering where compatible. Keep the existing frozen fixture parser and signed validator separate. Show the rest of the C0 design as reference context if useful, visibly separate from the delivered Intro. Preserve proposal preview, projection and artifact digests as distinct linked evidence.
5. **Close the visible loop.** In the private customer-facing view show the delivered Intro, its revision and “Ready for review.” Return to the Operator and show the real receipt and next review action. Label customer sign-in, full-site approval and an example Ongoing recommendation as future or simulated. Use existing refusal checks and add only seam-specific checks for wrong scope, stale approval or mismatched artifact, including refusal to display a different stage. Confirm public output and active state are untouched in the isolated test.

**Requested decision.** Approve a first walkthrough with one delivered text-only Intro, an adjacent reference to the existing Core Asset/AssetUsage proof and a clearly pending customer site decision. This narrows Issue #12's proposed asset-in-WordPress acceptance. If the first milestone must render a signed media asset or materialize native WordPress Pages, review that extension separately. The current reviewed projection rejects media bindings and Actions, and the frozen preview does not establish native WordPress generation.

**Smallest implementation after approval.** Add one scoped read-model connection between the interview draft, proposal and receipt, plus one staged-object preview input. Then run the existing protected delivery integration against the selected candidate. Replace the deterministic provider through Issue #10 after its independent data and spend gate, replace the local customer review view with authenticated exact site approval, and replace the example observation with first-party events and an Ongoing attention record. These replacements retain the same scope and approval boundaries.

Phase A publishes this decision for review. Implementation, provider spend, hosted operations, customer knowledge promotion, approvals on real records, native WordPress generation and publication remain gated.
